# 当前问题与限制

更新日期：2026-09-08

本文记录 Phase 0.3 真机验证完成后，当前实现仍然存在的已知问题、能力边界和未验证项。它描述的是当前代码与实际部署状态，不代表所有条目都必须进入下一版本。

## 1. 当前可用边界

当前链路已经能够在 HUAWEI Mate 60 Pro 上读取验证码通知，在手机本地提取 OTP，并通过自建 Bark Server 推送至 BarkMac。前台、后台和锁屏场景已经完成真实短信验证。

当前数据链路为：

```text
HarmonyOS → HTTP → Mac 上的 Bark Server → BarkMac
```

因此当前版本依赖以下条件：

- 手机必须能够访问 Bark Server；现有部署通常要求手机和 Mac 位于同一个可互通的局域网。
- Mac 必须保持联网，Docker 和 Bark Server 必须处于运行状态。
- BarkMac 必须已注册到当前 Bark Server，并保持 SSE 连接。
- 手机配置中的 Mac 局域网地址必须仍然有效。

## 2. 功能问题

### 2.1 首页状态不代表真实在线

首页的“正在转发”由通知授权、设备订阅、配置完整性和启用开关共同决定，但不会主动检查 Bark Server 或 BarkMac 是否在线。

因此可能出现以下误导状态：

```text
首页显示“正在转发”
但 Mac 已睡眠、Bark Server 已停止或网络已经断开
```

“保存并测试”可以验证当时的 HTTP 连接，但冷启动后只显示“已配置”，不是持续健康检查结果。

### 2.2 Bark Server 地址依赖固定局域网 IP

手机当前使用 Mac 的局域网 IP。DHCP 重新分配地址、切换路由器或切换 Wi-Fi 后，配置可能失效。当前没有服务发现、主机名解析兜底、地址迁移提示或自动更新。

### 2.3 没有发送队列和失败重试

每条 OTP 只执行一次 HTTP 请求。连接失败、超时或服务端返回非 2xx 时，该条 OTP 会丢失。当前没有：

- 内存发送队列
- 有限重试
- 指数退避
- 过期时间判断
- 网络恢复后的补发
- 应用层 ACK

### 2.4 没有来源 App 白名单

当前会解析所有收到的通知，只依赖文本关键词和数字规则决定是否推送。尚未限制为“信息”、银行或用户手动选择的应用，因此仍存在其他 App 通知被误判的可能。

### 2.5 OTP 识别仍是启发式规则

当前 Parser 使用关键词、关键词邻近位置、4–8 位数字和少量排除上下文。尚未实现置信度评分，也没有覆盖所有银行、邮箱、海外服务和复杂通知模板。

已知边界包括：

- 同一通知出现多组相关数字时可能选错或拒绝。
- 字母数字混合验证码不会识别。
- 全角数字、带空格或连字符的验证码不会识别。
- 新的订单号、金额、日期和尾号表达可能造成误判。
- 无法针对不同来源 App 使用独立规则。

### 2.6 去重能力有限

当前只记住最后一个 `source + code`，去重窗口为 60 秒，并且只存在于 Extension 内存中。Extension 被系统销毁或进程重启后，去重状态会丢失；交错到达的多条验证码也可能绕过单条记录模型。

### 2.7 缺少可见的运行历史和诊断信息

首页没有最近接收时间、最近发送结果、失败次数和最近 10 条脱敏历史。出现漏发时只能依赖开发工具读取 Hilog，不利于日常排障。

### 2.8 自动复制尚未实现

当前依赖 BarkMac 展示 macOS 通知，没有项目自有的剪贴板控制、自动复制开关、快捷键或剪贴板定时清理。

## 3. 纯蓝牙能力尚未实现

当前蓝牙只用于选择已配对设备并激活 HarmonyOS 通知订阅，不负责传输 OTP。手机与 Mac 不在同一可互通网络时，现有 HTTP 链路不能工作。

仓库中的 RFCOMM、JSON Lines 和原生 macOS Receiver 内容仍然属于设计方案，尚未实现以下 Gate：

- macOS 发布 RFCOMM/SDP 服务
- HarmonyOS 建立 SPP/RFCOMM 连接
- 手机发送静态 `hello-from-harmony`
- 半包、粘包和非法帧处理
- 断开重连与发送队列
- OTP JSON 协议传输
- macOS 通知与可配置剪贴板功能
- 后台、锁屏、睡眠和唤醒状态验证

纯蓝牙路线需要自研 macOS 接收端，现有 BarkMac 不能直接接收 RFCOMM 数据。

## 4. 可靠性未验证项

Phase 0.3 已验证单次前台、后台和锁屏短信链路，但尚未完成以下稳定性测试：

- BarkMac 登录启动和长期常驻
- Mac 睡眠、唤醒后的 SSE 恢复
- Docker 或 Bark Server 重启后的恢复
- 手机切换 Wi-Fi、移动数据和飞行模式后的恢复
- 手机蓝牙关闭再开启后的通知订阅状态
- Mac 局域网 IP 变化后的行为
- 多条 OTP 短时间连续到达
- Extension 被系统销毁后的首次消息
- 24 小时 soak test
- 大量通知下的误判率、漏判率和延迟统计

## 5. 安全与隐私限制

### 5.1 当前使用明文 HTTP

手机向 Bark Server 发送的请求包含提取后的 OTP。当前局域网部署使用 HTTP，没有 TLS，因此只适合可信网络，不应直接通过路由器端口映射暴露到公网。

### 5.2 缺少消息级认证

当前主要依赖 Bark Device Key，没有额外的 Device ID、配对密钥、HMAC、Nonce 或重放保护。尚不能从协议层验证消息确实来自已绑定的手机，也不能阻止合法请求被重复播放。

### 5.3 Device Key 使用普通 Preferences 保存

Device Key 保存在 HarmonyOS 应用 Preferences 中，虽然不会进入日志或仓库，但尚未迁移到更强的系统安全存储方案。

### 5.4 锁屏通知可能展示 OTP

BarkMac 系统通知会包含验证码。macOS 锁屏通知预览策略由系统和用户设置决定，当前项目不能保证旁观者无法看到 OTP。

### 5.5 日志脱敏尚未完全收敛

代码已经停止输出完整 `NotificationInfo`、短信正文、OTP body 和 Device Key，但仍有以下元数据通过 `%{public}s` 或 JSON 写入 Hilog：

- 通知标题和解析后的 `source`
- Bark 消息标题
- 已配对设备名称和蓝牙地址
- 通知订阅信息和取消通知的 hash code

通知标题或 `source` 在部分模板中可能包含验证码或较长的原始文本，因此目前不能严格保证日志永远不包含 OTP。蓝牙地址也属于不应长期公开记录的设备标识。需要改为 bundle allowlist、固定事件码、长度信息和掩码标识。

## 6. 部署与运维限制

- 当前安装包是开发调试签名，不是正式发布包。
- 本机签名证书和密码不会提交到 Git；在新的开发环境重新构建并安装时，需要重新完成 DevEco 自动签名和受限权限配置。
- Bark Server 由本机 Docker 承载，尚未纳入项目的一键启动、登录启动或健康监控。
- 当前没有配置迁移、备份和版本升级测试。
- 应用没有自动更新机制。

## 7. 文档一致性问题

项目早期文档以 Bluetooth SPP/RFCOMM 为主链路，Phase 0.3 实际 MVP 已切换为 Bark HTTP。`ARCHITECTURE.md`、`HARMONYOS_IMPLEMENTATION.md`、`MACOS_IMPLEMENTATION.md`、`PROTOCOL.md` 和根目录 `AGENTS.md` 中仍保留较多蓝牙目标架构内容。

这些内容目前应理解为“未来纯蓝牙方案”，而不是已经实现的现状。后续需要统一标注 Current Architecture 与 Future Bluetooth Architecture，避免开发者误判完成度。

## 8. 自动化测试缺口

当前自动化测试只有 11 个 OTP Parser 用例。以下模块和行为尚无自动化测试：

- `NotificationExtractor` 字段缺失和不同通知模板
- `ConfigService` 保存、读取、规范化和异常路径
- `BarkPushService` 2xx、非 2xx、超时和连接失败
- Extension 内的 60 秒去重逻辑
- 转发开关关闭时不发送
- 多条并发通知和请求生命周期
- 首页状态组合与配置交互
- 真机授权、订阅、后台和锁屏流程

Phase 0.3 的真机结果证明当前样本链路可用，但不能替代这些回归测试。

## 9. 建议的后续 Gate

如果优先提高当前 Bark 路线的日常可靠性，建议按以下顺序：

1. 来源 App 白名单与更高置信度 OTP 识别。
2. Bark Server 真实健康状态、发送队列、有限重试和过期丢弃。
3. BarkMac、Docker、Mac 睡眠唤醒和 24 小时稳定性验证。
4. HTTPS、消息认证和重放保护。

如果优先解决“不在同一局域网”的使用场景，建议单独开启 Bluetooth Gate：

1. macOS 最小 RFCOMM listener。
2. HarmonyOS 发送静态测试帧。
3. 连续发送和断开重连验证。
4. Gate 通过后再接入 OTP、通知和剪贴板。
